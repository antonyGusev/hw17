## REGRESSION-LAMP-004 — Blink peak brightness differs from solid brightness on FW 1.5.0 (regression)

| Field | Details |
|---|---|
| **ID** | `REGRESSION-LAMP-004` |
| **Issue type** | **Regression** |
| **Title** | Blink peak brightness differs from solid brightness on FW 1.5.0 (regression) |
| **Found in** | `1.5.0` |
| **Other firmware stages in this run** | `1.3.0`: Not observed (test not in FAILED list), `1.4.0`: Not observed (test not in FAILED list) |
| **Severity / Priority** | **Major / Medium (proposed)** |
| **Requirement(s)** | **FR-L5** |
| **Test Case ID** | `TC-LAMP-012` |
| **Automated test** | `tests/lamp/test_04_lamp_brightness.py::test_brightness_applies_in_all_modes[blink-3.0]` |
| **Category** | Suspected 1.5.0 firmware regression; optical method needs validation |
| **Reproducibility** | **1 failed pytest case(s) in 1 supplied run**; no independent rerun count |

**Preconditions**

- DUT 1.5.0; lamp on, set white at brightness 30.
- HIL camera available with existing exposure configuration.

**Steps to reproduce**

1. Set mode `solid`; measure brightness with the HIL photo module.
2. Set mode `blink`; measure max brightness over 3 seconds with the video module.
3. Compare results using 10% relative tolerance.

**Expected result:** Maximum intensity in the ON phase of blink agrees with solid-mode intensity within 10% under comparable camera conditions.

**Actual result:** On 1.5.0, `solid=23.0`, `blink=56.0` (approximately +143% relative); 1.3.0 and 1.4.0 did not fail this scenario.

**Evidence — UART / pytest**

```text
test_brightness_applies_in_all_modes[blink-3.0]
assert 56.0 == 23.0 ± 2.3
Obtained: 56.0
Expected: 23.0 ± 2.3
```


**Video evidence:** A previous `mode_blink.mp4` is present in the HIL archive, but it was not generated by this failed brightness-measurement call. It is **not used as direct evidence** of the intensity assertion.

**Note:** The test compares a photo-measurement statistic with a video-measurement statistic; varying camera auto exposure can influence the result. It nevertheless passes on prior versions and is a credible regression candidate. Do not relax tolerance pending repeat runs with fixed exposure. `mode_blink.mp4` in the failed folder was recorded earlier and does not constitute direct evidence for this measurement.

**Preconditions**

- DUT has no active Wi-Fi; UART console reachable.
- No OTA download is in progress.

**Steps to reproduce**

1. Check that the DUT is disconnected from Wi-Fi.
2. Execute `ota-test-server` via the test/controller.
3. Compare the response to the expected OTA error-message contract.

```text
ota-test-server

```


**Photo/video:** No direct image/video artifact for this UART-based failure in the supplied project.

**Note:** Missing Wi-Fi rejection behavior works; the observed discrepancy is **format**, not failure to block OTA. Confirm whether the exact prefix is part of firmware requirements; otherwise change the parser rather than claiming a firmware defect.
